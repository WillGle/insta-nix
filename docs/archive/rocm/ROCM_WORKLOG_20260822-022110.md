(HIP/Triton kernels, QLoRA) run on the 780M (gfx1103) despite gfx1103 being
absent from Unsloth's support matrix (Full support stops at gfx1100-1102 +
gfx1150-1152)? Plan: spoof gfx1102 via `HSA_OVERRIDE_GFX_VERSION=11.0.2`
(scoped to the container only — never global, protects DaVinci's OpenCL ICD).

## Final conclusion (2026-08-22, deeper experiments)

**Safe envelope for local QLoRA on gfx1103 (ROCm 7.2 wheels + spoof 11.0.2):**
- LoRA targets: attention only (q/k/v/o). **NEVER gate/up/down_proj** —
  Unsloth's manual-autograd MLP kernel hangs MES reproducibly (~2 min).
- Attention: default math path. **NEVER TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1.**
- No native gfx1103 binaries in the wheels (no-spoof = instant segfault);
  the 11.0.2 spoof is mandatory.
- Inside that envelope: 4B/seq1024/batch2 ran 100 steps / 19.6 min clean at
  performance clocks, 11.7 s/step, peak 3.28 GiB, Tctl 58°C. Both power
  profiles stable. Thermals are a non-issue at 4B scale.
- Crash cost collapsed vs March: MODE2 reset recovers in ~5 s, session
  survives (kernel 6.12.93). 3 GPU resets this session, zero logouts.
- Still untested: batch >2, ctx >1024, multi-hour runs, other model families.

## Conclusion v2 (2026-08-22, supersedes "Final conclusion" above)

1. Hard triggers stand: AOTriton flag and MLP-LoRA targets fail fast (3/3
   combined). Avoid both, always.
2. The qkvo envelope is REAL but conditional: 19.6 min clean sustained load is
   achievable — evidence says on reasonably-fresh MES state only. After ≥3
   GPU resets in a boot, even safe configs fast-fail (2/2).
3. Multi-hour trustworthiness: UNPROVEN. Next attempt must start from a fresh
   reboot; if a clean-boot 2h soak passes, the envelope upgrades for real.
4. Practical rule for real fine-tunes: reboot → performance profile → qkvo
   QLoRA + default attention → checkpoint every 50 steps → if ANY reset
   occurs, reboot before resuming.

## Conclusion v3 (2026-08-22, FINAL — supersedes v1/v2)

**Local PyTorch/Unsloth training on gfx1103 is STOCHASTIC and NOT usable for
real work.** The same 4B qkvo QLoRA config: 1× ran 100 steps/19.6 min clean,
4× hung MES at the first training step — across fresh boots, accumulated-reset
states, both power profiles, identical scripts. No controllable variable
predicts survival. "MLP-LoRA" and "AOTriton" (3/3 fast fails) are best read
as higher-intensity lanes of the same underlying MES fragility, not distinct
root causes. This matches AMD/Unsloth excluding gfx1103 from their support
matrices.

What SURVIVES from the campaign:
- ROCm 7.2 spoofed compute is functionally correct when it runs (matmul
  values, decreasing loss, saved adapters) — fine for short throwaway
  experiments if you accept ~80% instant-fail odds per attempt.
- 0.6B-scale canary passed cleanly; small models may have lower crash odds
  (2 clean runs incl. matmuls; not systematically tested).
- A MES hang costs ~5 s (MODE2 reset, session survives, kernel 6.12.93) —
  cheap to retry, impossible to trust.
- Vulkan/llama.cpp inference (llm-run) is a completely separate, stable lane
  — unaffected throughout (multiple GPU resets, zero inference impact).

**Recommendation (back to ML_GPU_COMPUTE first principles): real fine-tuning
= cloud GPU (Unsloth QLoRA on a rented card, export GGUF, serve locally via
llm-run). Local gfx1103 GPU training = demo/learning only.** The container
stays for that purpose.
